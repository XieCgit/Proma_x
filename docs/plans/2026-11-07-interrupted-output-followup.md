# 停止与异常输出恢复：后续集成要点

## 当前状态

`apps/electron/src/main/lib/interrupted-output.ts` 是已编写单元测试的实验性纯内存缓冲，**未接入运行时**。它不能单独保证停止后保存回复，更不能保证下一轮模型能看到中断文本。

当前社区版在启动预检异常时新增了运行槽释放保护；这不等于完成了停止、断线、重试及恢复的端到端修复。不要从单元测试通过推断这些场景已经解决。

## 审查中核实的关键约束

1. Pi 的 `transform-messages.js` 会跳过 `stopReason` 为 `aborted` 或 `error` 的 assistant 消息。仅把流式片段写入应用 JSONL，无法确保 Pi 原生恢复时会将其发给模型。
2. `AgentOrchestrator.stop()` 会在底层 adapter 真正收束前释放活动槽，新运行的预检可能先保存新的用户消息；旧运行若之后追加中断回复，会造成消息跨代际乱序。单靠在原 `catch` 中 `drain()` 并写盘不安全。
3. Pi 的同 UUID 原生重试、`assistant.error` 已带文本、空终态、正常 result 提前到达，以及会话删除，都需要独立处理，避免残片拼接、重复保存、顺序错误和删除后复活。
4. `InterruptedOutputBuffer` 当前在 `start` 时清除同 UUID 内容。真实 Pi 事件序列与重试阶段需要专门验证，不能假定每次重试都会发出该标记。超过 UUID 上限时当前实现会逐出旧项，属于有界但可能丢失内容的行为，也不能称为无损。
5. 被强制终止的主进程或尚未送达主进程的增量不能靠内存缓冲恢复；中断时工具副作用也不能靠文本回放恢复。

## 建议的实施顺序

1. 为停止后的旧运行收束建立按 session 和 generation 识别的排空屏障，并验证新运行在旧运行持久化完成前不会写入新用户消息或覆盖旧运行元数据。要考虑预检、排队、headless、删除和超时，避免死锁。
2. 对适配器生成的原生重试与终态消息建模。仅保留可见文本；与已收到的完整 assistant 互斥，禁止保留未执行的工具调用或不应回放的隐藏推理。
3. 在 `result` 之前按正确顺序落盘，错误回退重试不得混入失败尝试；明确标记截断或未能保留的文本。
4. 选择并实现经验证的 Pi artifact 一致性方案，或在中断后有条件回退到应用历史构造上下文。必须同时验证后续请求、fork/rewind 和 metadata，不在旧代收束时覆盖新代恢复指针。
5. 用 fake adapter / fake stream 和临时目录构建集成测试，再在隔离系统账户或虚拟机中进行桌面验证。

## 最低测试矩阵

- 停止后立即启动下一轮：确保 `用户 1 → 部分回复 1 → 用户 2 → 回复 2`，旧代不覆盖新代状态。
- 同 UUID 重试后产生新文本、重试前停止、重试空失败：不拼接旧片段，也不丢弃已显示但未被替代的文本。
- 终态错误包含文本与空文本两种场景：正文恰好保存一次，正文早于错误提示，剔除不应回放的块。
- 只有 delta 而无完整 assistant 即到达 result：正文先于 result，不误判为空回复。
- `session-not-found`、thinking signature 和上下文超限自动回退：失败尝试残片不污染成功结果。
- 中断后再发送时，实际捕获传给模型的消息，确认包含期望的部分回复，并测试 fork/rewind。
- 删除会话与停止并发：迟到事件不得重建文件。
- 超长截断、进程强杀、Utility Process 意外退出及异常响应：区分可恢复和不可保证情形。

本文件是设计与待测项，不是已通过的验收报告。任何实现仍需对照实际上游 Pi 版本和许可进行审查。
